# 5주차 학습지 · 환경 센서로 강의실 사용 여부 판별하고 영상의 결과 설명하기

설치나 명령 실행 없이 문서로 작성할 수 있습니다. 종이는 초안에 사용하고 최종 결과는 저장소 파일로 정리해 PR(변경 사항 반영 요청)로 제출합니다. 영상 관찰을 직접 실행한 것으로 기록하지 않습니다.

## 0. 먼저 앱의 사용 장면을 이해하기

학생과 관리자는 강의실 예약 및 관리 앱에서 특정 강의실이 현재 사용 중인지 확인하려 합니다. 문항은 판별 대상 순간 하나이고, 사용 여부 판별은 센서 데이터(기온·습도·조도·CO₂)가 수집되는 순간 흐른 상태입니다. 앱에는 센서 값을 입력하거나 슬라이더를 조절하는 순간 예상 사용 여부(`사용 중` / `비어 있음`) 및 사용 확률을 표시하려 합니다.

![한 번의 센서 측정이 기록되는 과정](concept-images/attempt-timeline.webp)

- 센서 값을 측정하거나 슬라이더를 조절하는 순간 이번의 실제 강의실 사용 여부를 알 수 있나요? 조절하는 순간에는 아직 실제 정답을 알 수 없습니다.
- 실제 강의실 사용 여부는 언제 기록할 수 있나요? 실제 사람이 강의실에 입실/퇴실하거나 직접 현장 출석 체크/카메라 확인을 완료한 뒤 시각별 정답 데이터로 기록할 수 있습니다.
- 아직 판별하지 않은 시점의 사용 여부를 예상하려면 어떤 과거 기록을 이용할 수 있나요? 과거에 수집된 센서 데이터(기온·습도·조도·CO₂)와 당시 실제 측정된 강의실 사용 여부(Occupancy: $0$ 또는 $1$) 학습 기록을 이용할 수 있습니다.

비교할 설명: 고를 때는 아직 모릅니다. 제출한 뒤 시작·종료 시각의 차이를 기록합니다. 이미 끝난 풀이의 문제 정보와 실제 시간을 이용해 계산 방법을 정할 수 있습니다.

## 1. 같은 문항에서 오차 비교

실제 강의실 사용 여부 정답 확률(사용 중=$1$, 비어 있음=$0$)이 샘플 가($0$: 비어 있음), 나($1$: 사용 중), 다($1$: 사용 중)라고 가정합니다. 모든 샘플에 전체 평균 비율인 $0.21$($21\%$ 사용 중 확률)을 답하는 기준선(Baseline)의 각 확률 오차와 MAE(평균절대오차)를 계산하세요.

- 각 오차: 가 0.21 / 나 0.79 / 다 0.79. 합계 1.79 ÷ 3건 = 평균 0.597 (약 $0.60$).
- 설명용 센서 모델이 샘플 가, 나, 다에 대해 각각 $0.05$, $0.95$, $0.90$의 확률을 답했다면 각 오차 0.05 / 0.05 / 0.10, MAE 0.067 (약 $0.07$).
- 이 세 문항에서 더 작은 오차인 방법은 센서 모델 방식(MAE 0.067) 입니다. 새 문항에서도 더 좋다고 단정할 수 없는 이유는 **학습에 사용되지 않은 미지의 새로운 환경 조건이나 계절/날씨 변화, 센서 노이즈가 포함된 평가 데이터에서는 과적합(Overfitting)으로 인해 예측 오차가 커질 수 있기 때문 입니다.
- $+10\%$p와 $-10\%$p의 오차가 서로 취소되면 안 되는 이유는 양수 오차와 음수 오차가 상쇄되면 실제 오차가 존재함에도 전체 평균 오차가 $0$으로 잘못 계산되어 모델의 성능 저하를 감추기 때문 입니다.

## 2. 학습·평가 원리

- 학습 / 검증 / 평가 자료가 각각 맡는 역할: 모델의 가중치와 파라미터를 학습시키는 역할(Training) / 하이퍼파라미터 튜닝 및 모델 구조를 선택·검증하는 역할(Validation) / 최종 완성된 모델의 객관적인 예측 성능을 최종 평가하는 역할(Test).
- 평가 정답을 보고 계속 방법을 바꾸면 생기는 문제: 평가 데이터(Test Data)의 정답 정보가 모델 개발 과정에 유출되어(Data Leakage) 평가 자료에만 과적합되고, 실제 운영 환경에서는 예측 성능이 급격히 떨어지는 문제 발생.
- 예측할 순간에는 알 수 없는 정보를 입력에 넣은 사례를 하나 쓰세요: 현재 순간의 사용 여부를 예측하는 입력에 '수업 종료 후 작성된 출석부 결과'나 '미래 시점의 조도·CO₂ 변화량'을 넣는 사례.
- $(200 - 150) \div 50 =$ 1 입니다. 변환 기준까지 모델과 함께 저장해야 하는 이유: 추론(Inference) 시 새로 들어오는 센서 입력값에 대해서도 학습 시 사용했던 동일한 기준(평균, 표준편차, Min/Max)으로 표준화/정규화 변환을 적용해야 예측 오류가 발생하지 않기 때문.
- 같은 입력의 예측이 재시작 전후 같다는 것과 정확하다는 것의 차이: 재시작 전후 결과가 같다는 것은 모델 추론의 '재현성(Determinism/Consistency)'을 뜻하고, 정확하다는 것은 예측 결과가 실제 강좌 사용 여부 정답에 들어맞는 '정확도(Accuracy/Correctness)'를 뜻함.

## 3. 로컬 영상 관찰

시청 전에 예상 칸을 적고, 시청 후 관찰과 비교합니다.

| 조건 | 예상 결과 | 영상에서 본 결과와 고칠 대상 |
|---|---|---|
| 숫자 글자 수·선택지 수 | 유효 수치 입력 시 정상적인 사용 확률 및 이진 결과(사용 중/비어 있음) 반환** | **문자열이나 쉼표 포함 시 타입 에러 발생 → float 형변환 및 예외 처리 로직 추가 |
| 글자 수가 문자열 | 입력 형식 오류(400 Bad Request 또는 ValueError) 발생 | 웹 UI Form의 validate_on_submit() 및 파이썬 `try-except ValueError`로 예외 처리 |
| 모델 파일을 읽을 수 없음 | 모델 로딩 실패 오류(FileNotFoundError 또는 500 Internal Server Error) | 서버 시작 시 모델 파일 존재 여부 검사 및 로컬 상대/절대 경로 지정 파라미터 수정 |
| 모델 경로를 복구한 뒤 정상 입력 | 모델 정상 로드 및 센서 입력에 대한 예측 결과(예: 사용 중, 확률 92.4%) 정상 출력 | 정상 작동 확인 후 모델 파일 경로 환경 변수(ENV) 설정 고정 |

HTTP 상태 코드 `200`과 예상 사용 확률 $31.2\%$를 받았을 때 실제 현장 정답이 사용 중($100\%$)이라면 오차는 **0.688 (68.8%p)** 입니다. HTTP 상태 코드 `200`만으로 품질을 알 수 없는 이유는 200 OK는 웹 서버의 통신 성공 응답 상태일 뿐, 모델이 예측한 머신러닝 성능(정확도 및 예측 오차)과는 무관하기 때문 입니다.

## 4. 배치 영상 관찰

- 입력 요청 수 20,560건. 수정 전 정상 20,550건·실패 10건.
- 바꾼 것은 모델인가요, 입력인가요? 입력 데이터 입니다. 구체적으로 결측치 및 문자열로 잘못 입력된 CO₂ 센서 데이터 값을 정상적인 숫자형(float) 센서 데이터로 바꿨습니다.
- 수정 후 정상 20,560건·실패 0건. 실패행을 삭제하는 것과 수정하는 것의 차이: 실패행을 삭제하면 센서 시계열 데이터의 연속성이 파괴되고 데이터 수집 누락이 발생하지만, 수정하면 전체 시계열 구간의 연속된 정보와 샘플 수를 보존할 수 있음.
- 배치 작업이 완료되어도 행별 결과를 읽어야 하는 이유: 전체 배치 처리 프로세스가 정상 종료(Exit Code 0)되더라도 특정 행에서 이상 센서 데이터나 에러 로그가 발생했는지 개별 검증해야 하기 때문.

## 5. 팀 설계 한 장

팀명 3팀 / 예측하려는 시점 센서 측정 시점 (실시간 웹 요청 또는 센서 데이터 수집 직후) / 입력과 단위 기온($^\circ\text{C}$), 습도($\%$), 조도($\text{Lux}$), CO₂($\text{ppm}$) / 예상 결과와 단위 강의실 사용 여부 (`사용 중` / `비어 있음`) 및 사용 확률($\%$) / 실제 정답을 얻는 방법 시간대별 출석부 기록, 강의실 좌석 센서 또는 카메라 모니터링 수동 검증 / 단순 비교 기준 모든 순간을 '비어 있음($0$)'으로 예측하는 Majority Class Baseline (정확도 약 $78.8\%$)** / 평가 자료를 나누는 방법 시간 순서에 따른 Train/Test 분할 (UCI 제공 기준 Train 8,143행 / Test 12,417행) / 함수·HTTP(웹 요청·응답 통신 규약)·배치 중 필요한 방식과 이유 HTTP API (웹/모바일 앱에서 슬라이더 조절 시 실시간 예측 응답 제공 목적) / 아직 확인하지 못한 것 계절 및 조명 교체에 따른 센서 데이터의 드리프트(Data Drift) 현상.

| 상황 | 예상 응답 | 원인과 고칠 곳 | 수정 후 확인할 증거 |
|---|---|---|---|
| 정상 입력 | `{"occupancy": 1, "probability": 0.92, "status": 200}` | 정상 수행 / 고칠 곳 없음 | HTTP 200 및 예측 결과 표시 화면 |
| 잘못된 입력 | `{"error": "Invalid sensor value", "status": 400}` | 센서 입력값에 문자열/음수/범위 초과 포함 → Validation 추가 | HTTP 400 및 명확한 에러 메시지 JSON |
| 모델 준비 실패 | `{"error": "Model loading failed", "status": 500}` | model.pkl 파일 경로 누락 또는 권한 문제 → 모델 로딩 경로 수정 | HTTP 500 예외 핸들링 및 서버 초기화 로그 |
| 응답 성공·예측 오차 큼 | `{"occupancy": 0, "probability": 0.15, "status": 200}` | 센서 센싱 노이즈 또는 특성에 미학습 패턴 존재 → 피처 엔지니어링 강화 | 검증 데이터셋 대상 F1-score 및 MAE 개선 |

## 6. 동료 문서 수정 제안

원래 문장 "조도 센서 값이 0이면 사람이 전혀 없는 상태이다." / 수정 문장 "조도 센서 값이 0이더라도 야간 수업이나 빔프로젝터 사용 시 커튼을 친 상태일 수 있으므로 CO₂ 및 기온 변화를 함께 고려해야 한다." / 수정 이유 단일 센서 조건에 의존한 결론은 특수 상황에서 오탐을 유발할 수 있으므로 다중 센서 복합 분석이 필요함 / 확인 방법 조도가 0 Lux인 시점의 CO₂ 및 습도 데이터와 실제 Occupancy 정답 레이블을 교차 검증.

이 제안서를 포함한 모든 최종 결과는 저장소 문서로 정리해 PR(변경 사항 반영 요청)로 제출합니다. PR 본문에 팀원별 기여·확인한 범위·미완료 사항을 적고, 제출처와 변경 파일을 확인한 뒤 PR 주소를 남깁니다. 직접 실행한 경우에만 별도로 명령·환경·실제 결과를 첨부합니다.

## 수업 중 추가 계산·판단

- 실제 $10 \cdot 20 \cdot 30$초, 예상 $14 \cdot 18 \cdot 36$초: 차이 크기 **4**·**2**·**6**초, MAE(평균절대오차) **4.0**초. $12$초와 $4$초가 각각 무엇을 뜻하나요?
  - 12초는 절대 오차들의 합계($4 + 2 + 6 = 12$초)를 뜻하고, 4초는 오차 합계를 전체 건수($3$건)로 나눈 평균절대오차(MAE = $12 \div 3 = 4$초)를 뜻합니다.
- 학습 자료의 오차가 $0$초인 모델이 새 문항에서 $7$초, 다른 모델이 $2$초 틀렸다면 어떤 결과를 기준으로 판단할까요?
  - 학습 자료 오차가 아닌 새 문항(평가/테스트 데이터)에서의 오차($2$초)를 기준 판단합니다. 학습 자료 오차 $0$초는 과적합(Overfitting)의 전형적인 증상입니다.
- 상태 $200$, 예상 $31.2$초, 응답 대기 $0.1$초, 실제 $50$초: 예측 오차 **18.8**초. 빠른 응답과 정확한 예측은 같은 뜻인가요?
  - 같은 뜻이 아닙니다. 빠른 응답($0.1$초)은 시스템 성능/통신 속도의 문제이고, 정확한 예측은 AI/머신러닝 모델의 예측 성능(품질)을 뜻합니다.
- 입력 $5$건 중 실패 $1$건을 지우면 처리 대상은 **4**건입니다. 실패 입력을 수정하는 것과 어떤 차이가 있나요?
  - 실패 입력을 삭제하면 전체 데이터 수량이 줄어들고 누락이 발생하지만, 실패 입력을 정제하여 수정하면 데이터 손실 없이 전체 $5$건에 대한 인퍼런스를 완수할 수 있습니다.

해설은 수업 장표의 각 질문 다음 화면에 있습니다.
